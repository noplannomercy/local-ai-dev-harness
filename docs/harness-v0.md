# Harness 구성안 v0

- 작성일: 2026-10-04 (3자 검토 반영 개정)
- 상태: **검토용.** 사용자·GPT·Claude 검토를 거쳐 구조를 확정한 뒤 실물 구성에 들어간다. 이 문서 작성 시점에 설치·설정·테스트는 하지 않았다.
- 근거: `docs/research-result-claude.md` (본문, Addendum, 결론)
- 대상: 이 프로젝트 폴더(`C:\workspace\harness`)가 배포 가능한 Local AI Development Harness의 원형이다.

## 1. 목표와 원칙

### 합격 기준

> 새 개발자가 이 하네스를 받아 설치하고, 자기 프로젝트를 붙이고, Claude Code를 켜서 FE+BE 코드를 찾고 → 수정하고 → 실행하고 → 브라우저로 확인하고 → 테스트까지 끝낼 수 있다.

이 문장에 기여하지 않는 것은 넣지 않는다.

### 원칙

1. **작동하는 최소 개발환경을 먼저 제공한다.** 위 합격 기준에 필요한 것은 처음부터 넣는다.
2. **고유 가치가 불명확한 보강층만 비워 두고 비교한다.** agent 내장 기능과 겹치는 층은 실제 조건에서 평가한 뒤 승격하거나 탈락시킨다.
3. **Harness Core와 Project Profile을 분리한다.** Core는 프로젝트와 무관하게 만든다. 스택에 따라 달라지는 것은 Project Profile에 둔다. 하네스가 특정 저장소 하나를 전제로 만들어지면 안 된다.
4. **능력과 구현을 분리한다.** "브라우저로 확인할 수 있어야 한다"는 능력이고 어떤 도구로 하느냐는 구현이다. Core에는 능력을 고정하고, 구현은 가장 가벼운 것을 고르며 바꿀 수 있게 둔다.
5. **agent가 이미 하는 일을 다시 만들지 않는다.** 일하는 순서를 가르치는 지침·skill은 넣지 않는다. 넣는 것은 모델이 알 수 없는 사실(이 프로젝트의 빌드·실행·검증 방법)과 환경을 재현하는 수단이다.
6. **상시 주입은 짧게 유지한다.**
7. **특정 벤더에 전체가 묶이지 않게 한다.** 재사용 가능한 규칙은 공통 포맷(AGENTS.md, Agent Skills, 일반 CLI)에 둔다. 다만 최저 공통분모에 맞추느라 기본 agent의 기능을 버리지는 않는다.

## 2. 구성

### 2.1 Harness Core (프로젝트 없이 지금 만들 수 있는 것)

| 구성요소 | 내용 | 구현 상태 |
|---|---|---|
| **Agent** | 기본: Claude Code. 호환: Codex CLI, OpenCode | 확정. 선정 근거: 환경 B의 공식 managed-model 지원, 국내 유사 적용 선례, 팀의 실사용 경험과 숙련도. 호환 agent는 교차 검토와 환경 C fallback 경로 |
| **모델 접근 경로** | 직결 ↔ Bedrock ↔ 게이트웨이를 설정 교체로 바꾸는 지점 | 확정. 이것이 없으면 "B의 원형"이 아니다 |
| **보안·정책** | 권한 허용·차단, 비밀 파일 읽기 차단, provider·모델·리전 고정, 조직 정책 템플릿 | 확정 |
| **공통 지침** | 짧은 공통 규칙 + 완료 전 검증 규칙(빌드·테스트·화면 확인 없이 완료라고 하지 않는다) | 확정. 서너 줄 수준 |
| **브라우저 확인 능력** | agent가 화면을 보고 조작할 수 있어야 한다 | 능력 확정. **구현은 Core 구성 때 하나를 고른다** (CLI, agent 내장 브라우저, MCP 중 가장 가벼운 것) |
| **문서 조회 능력** | 모델 학습 시점 이후의 라이브러리·프레임워크 문서를 조회할 수 있어야 한다 | 능력 확정. **구현 후보에 Context7 포함.** 외부 서비스 의존이라 환경 B 원칙과 충돌할 수 있으므로 전송 내용·인증·허용 가능성을 확인한 뒤 고른다 |
| **Bootstrap** | `setup`(PC에 Core 설치), `check`(agent·런타임·브라우저·모델 경로 연결 점검) | 확정. Windows 네이티브 배포가 목표이므로 PowerShell |
| **Project onboarding** | `init-project <경로>`: 대상 저장소에 프로젝트 지침·설정·검증 틀을 넣는다 | 확정. PC 설치와 대상 저장소 설정을 잇는 계층. 아래 "onboarding 범위" 참조 |
| **Quickstart** | 설치부터 첫 작업까지 5~10분 안내 | 확정 |

**onboarding 범위**: 처음부터 스택 자동 판별기를 만들지 않는다. agent는 저장소를 읽고 프로젝트 지침 초안을 만드는 기능을 이미 갖고 있으므로, `init-project`는 틀을 넣고 agent에게 프로젝트 사실(빌드·실행·테스트·화면 확인 방법)을 채우게 하는 얇은 연결로 시작한다.

### 2.2 Project Profile (대상 프로젝트의 스택에 따라 붙는 것)

실제 프로젝트가 붙을 때 채운다. Core에는 빈 틀만 둔다.

| 항목 | 내용 |
|---|---|
| **빌드·테스트·실행 명령** | 프로젝트 지침에 몇 줄로 적는다 |
| **LSP** | 스택에 맞는 내장 LSP 플러그인과 언어 서버 |
| **브라우저 검증 방법** | 앱을 띄우는 방법, 확인할 주소, 로그인 방법 |
| **`verify-change` skill** | 이 프로젝트의 빌드·테스트·실행·화면 확인 사실만 담은 좁은 skill. 지금은 템플릿만 둔다 |
| **DB 스키마 조회** | DB 종류와 접근 정책이 정해질 때 |
| **이슈·형상관리 연동** | 고객 시스템에 따라 |

### 2.3 Optional Enhancement (실제 조건에서 평가 후 승격)

| 후보 | 층 | 평가 조건 |
|---|---|---|
| **Serena** | Code intelligence | 내장 LSP와 파일 간 rename·심볼 편집에서 정면 비교. 이겨도 GPL 전환과 언어 서버 오프라인 배포 문제 때문에 "배포 검토 대상"이 된다 |
| **CodeGraph** | Code intelligence | 저장소가 커서 호출·의존 구조 탐색이 실제로 비싸질 때. 모델이 도구를 호출하지 않는 문제가 확인 포인트 |
| **Orca** | 개발 UX·운영 | 먼저 사용자 본인의 작업 환경으로 Claude ↔ GPT 왕복 마찰을 줄이는지 본다. 고객사 개발자 배포 적합성은 그 뒤의 별도 질문 |

Code intelligence는 **profile로 비교할 수 있게 설계해 둔다**: 내장만 / 내장 + Serena / 내장 + CodeGraph. 승부는 실제 업무급 저장소가 생겼을 때 본다. 작은 샘플 저장소의 결과를 일반화하지 않는다.

### 2.4 초기 0개로 두는 것

| 슬롯 | 채우는 조건 |
|---|---|
| **Hooks** | agent가 프로젝트의 기존 포맷터·린터·테스트 실행을 반복해서 빠뜨릴 때 |
| **그 외 MCP** | agent 기본 도구와 CLI로 안 되는 능력이 확인될 때 |
| **그 외 Skills** | 모델에게 같은 프로젝트 사실을 반복해서 알려 줘야 하는 것이 확인될 때 |

### 2.5 v0 기본 구성 제외

영구 제외가 아니다. 해당 결손이 실제로 확인되면 다시 올린다.

| 항목 | 이유와 돌아오는 조건 |
|---|---|
| Superpowers 전체 | agent 내장 기능과 중복이 크고 세션마다 강제 문구를 주입한다. 완료 전 검증은 공통 지침의 규칙으로 가져왔다 |
| gstack 전체 | 외부 API·자동 업데이트·Windows 이슈. 브라우저 QA는 브라우저 확인 능력으로, 교차 모델 리뷰는 호환 agent로 다룬다 |
| 일반 개발 순서 skill (`develop` 류) | agent가 원래 하는 순서를 다시 적는 것이라 조사 결과와 부딪친다 |
| Graphify 기본 탑재 | 편집 루프보다 저장소 이해 용도. 문서·SQL·설정까지 묶어야 하는 저장소를 만나면 다시 본다 |
| 벡터 RAG MCP | 외부 임베딩 API가 필요하고 agent 내장 탐색과 겹친다 |
| Jev | 사용자 결정으로 제외. agent의 판단이 같은 지점에서 반복해서 흔들릴 때 다시 본다 |

## 3. 디렉터리 구성안

```
harness/
├─ README.md                    Quickstart
├─ setup.ps1                    PC에 Core 설치
├─ check.ps1                    환경 점검
├─ init-project.ps1             대상 저장소에 프로젝트 틀 적용
├─ core/
│  ├─ AGENTS.core.md            공통 지침 (검증 규칙 포함, 짧게)
│  ├─ settings.core.json        권한, 비밀 파일 차단
│  ├─ capabilities.json         능력별 채택 구현
│  ├─ VERSION
│  ├─ providers/                모델 접근 경로별 설정
│  │  ├─ direct.json
│  │  ├─ bedrock.json
│  │  └─ gateway.example.json
│  └─ policy/
│     └─ managed-settings.example.json   조직 정책 템플릿
├─ profiles/
│  └─ _template/                Project Profile 빈 틀
│     ├─ AGENTS.project.md      빌드·테스트·실행·화면 확인 사실
│     ├─ fill-profile.prompt.md agent에게 프로젝트 사실을 채우게 하는 프롬프트
│     └─ skills/verify-change/SKILL.md
└─ docs/
```

- 스택별 profile(`profiles/<이름>/`)은 실제 프로젝트가 붙을 때 추가한다.
- Optional Enhancement용 디렉터리는 평가를 시작할 때 만든다.
- 호환 agent 설정(`.codex/config.toml`, `opencode.json`)은 실제로 쓸 때 추가한다.

### 설치되는 위치

| 단계 | 어디에 무엇이 들어가는가 |
|---|---|
| `setup` | 개발자 PC: agent 확인·설치, 조직 정책, 모델 접근 경로, 브라우저 도구, 문서 조회 도구 |
| `init-project` | 대상 저장소: `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json`, 필요 시 `verify-change` skill과 LSP 설정 |
| `check` | 위 둘이 제대로 들어갔는지, 모델 경로가 연결되는지 확인 |

## 4. 열려 있는 결정

Core 구성 중에 정하는 것:

1. **모델 접근 경로에 쓸 AWS 계정**: 이 PC에 다른 프로젝트의 AWS 자격증명이 있고 서울 리전에서 Claude 모델이 조회된다. 다른 프로젝트 계정으로 보이므로 이 하네스에 써도 되는지 확인이 필요하다. 안 되면 직결 설정만 실제로 검증하고 Bedrock 설정은 틀만 둔다.
2. **브라우저 확인 구현**: 후보를 붙여 보고 하나를 고른다.
3. **문서 조회 구현**: Context7의 전송 내용·인증·환경 B 허용 가능성을 확인한 뒤 고른다.

나중에 정하는 것:

4. **검증용 FE+BE 저장소**: 실제 고객 소스가 없으므로 대표 fixture를 가져오거나 만들어 Project Profile과 `init-project`를 검증한다. 그 결과를 모든 프로젝트에 일반화하지 않는다.
5. **Code intelligence profile 승부**: 업무급 저장소가 생겼을 때.
6. **Orca를 사용자 작업 환경으로 먼저 확인할지 여부.**

## 5. 이 구성안이 답하지 않는 것

- 게이트웨이, 감사 로그, 입력 차단 등 통제 구조의 설계. 후속 주제다.
- 환경 C용 구성. fallback이며, 필요해질 때 호환 agent 설정과 모델 서빙 구성을 따로 잡는다.
- 생산성 효과. 실물 구성 이후에만 확인할 수 있다.

## 6. 구현 기록 (2026-10-04, Core v0.1.0)

### 6.1 만들어진 것

3장의 구성안에서 달라진 점: `core/capabilities.json`(능력별 채택 구현), `core/VERSION`, `profiles/_template/fill-profile.prompt.md`(agent에게 프로젝트 사실을 채우게 하는 프롬프트)가 추가됐다. `init-project`는 대상 저장소에 `.claude/harness.json`(적용 상태)도 남긴다.

### 6.2 능력 구현 선택

후보 조사 → 선택 근거 → 하나 채택 순서로 정했다. 후보별 사실은 저장소 README, 공식 문서, npm 레지스트리에서 확인했다.

**화면 확인: Playwright CLI + PC에 설치된 Edge**

| 후보 | 판정 | 이유 |
|---|---|---|
| Playwright CLI (`@playwright/cli`) | **채택** | 설치된 Edge를 채널 옵션으로 구동하므로 브라우저 다운로드가 없다. 상주하는 도구 정의가 없어 컨텍스트 비용이 작다. 셸 명령이라 세 agent가 같은 방식으로 쓴다. Microsoft가 README에서 coding agent에는 MCP보다 CLI를 권한다 |
| Playwright MCP | 대체 경로 | 같은 엔진. 도구 정의 약 25개가 상주한다. CLI가 Windows에서 불안정하면 이쪽으로 바꾼다 |
| Chrome DevTools MCP | 탈락 | Edge 공식 지원이 없고 사용 통계 전송이 기본 켜짐이다. 성능 트레이스가 요건이 되면 다시 본다 |
| Claude in Chrome | 탈락 | Bedrock·게이트웨이에서 쓸 수 없다고 문서에 명시돼 있다 |

**문서 조회: 설치된 버전의 로컬 자료 읽기**

| 후보 | 판정 | 이유 |
|---|---|---|
| 로컬 소스·타입 정의·문서 | **채택** | 외부 통신이 없어 환경 B에서 승인받을 것이 없다. 실제 설치된 버전의 자료를 그대로 읽는다. 추가 제품이 없다 |
| 내장 WebFetch + 공식 문서 도메인 허용 목록 | 다음 단계 | 서술형 문서(마이그레이션 가이드 등)가 필요하고 네트워크 승인이 나면 추가한다 |
| Context7 (호스팅) | v0 미채택 | 검색 쿼리가 외부로 나가고, 콘텐츠가 커뮤니티 기여이며, 외부 SaaS 도메인 승인이 필요하다. 2026-02에 프롬프트 인젝션 경로가 보고되어 수정된 이력이 있다. 제약 없는 환경(A)에서 개인이 쓰는 것은 별개다 |
| Context7 (온프레미스) | 조건부 | Enterprise 계약 전용. 사내 비공개 라이브러리 문서까지 검색해야 할 때 |

### 6.3 실제로 검증한 것

이 PC(Windows 11, Windows PowerShell 5.1, Claude Code 2.1.289)에서 임시 폴더를 대상으로 실행했다.

| 항목 | 결과 |
|---|---|
| `setup.ps1` 보고 모드 | 통과. 설치할 것이 없어 `-Install` 경로는 실행되지 않았다 |
| `init-project.ps1` 신규 적용 | 통과 |
| `init-project.ps1` 재실행 | 통과. 변경 없음으로 보고 |
| provider 전환 (직결 → Bedrock → 직결) | 통과. 하네스가 넣은 키만 넣고 뺀다 |

### 8.4 향후 확장 방향 (working principle)

다음 확장은 **모델에게 개발 절차나 사고법을 더 주입하는 것보다, 코드 저장소 밖에 있어 모델이 원래 볼 수 없는 실제 개발 자원을 열어 주는 것**을 먼저 검토한다.

- Claude Code가 이미 수행하는 계획·리뷰·디버깅 workflow를 별도 framework로 중복 구축하지 않는다.
- 기존 도구가 해결하는 문제를 새 MCP·Skill·wrapper로 다시 만들지 않는다.
- native CLI가 충분하면 CLI를 우선한다.
- Project Profile을 프로젝트별 실제 stack과 외부 자원을 연결하는 위치로 쓴다.
- Optional Enhancement는 관찰된 결손이 있을 때만 추가한다.

이것은 절대 원칙이나 최종 아키텍처가 아니다. v0.1.0 이후의 확장을 판단하기 위한 작업 원칙이다.

### 8.5 확장 후보 inventory

**v0.1.0의 구성요소가 아니다.** 실제 프로젝트에 해당 외부 자원이 있고 필요성이 드러날 때 고르는 후보 목록이다. "이 PC" 열은 2026-10-05 조회 결과다.

| # | 영역 | 열어 주는 것 | 후보 도구 | 이 PC | 비고 |
|---|---|---|---|---|---|
| 1 | Data | 실제 스키마, 뷰, 프로시저, 실행 계획, 개발 데이터 | Oracle SQLcl, `psql`, `sqlcmd`, `mysql` | 전부 없음 | Oracle 환경이면 SQLcl 우선. 별도 MCP 개발을 전제하지 않는다. CLI 우선, 필요하면 SQLcl 내장 MCP 모드(`sql -mcp`) 활용. 개발 DB 한정·읽기 전용 계정이 전제 |
| 2 | Documents | DOCX·XLSX·PPTX 요구사항·설계 문서 | MarkItDown, LibreOffice headless, 기존 문서 skill | 있음 | 사람이 Markdown으로 다시 쓰지 않고 원본을 사용. HWP 변환기는 없음(고객 문서 형식 확인 후) |
| 3 | Runtime | 실행 중인 앱의 실제 상태 | `curl` + OpenAPI, Spring Boot Actuator, `jcmd`·`jstack`·`jdb` | 있음 | 코드 추론이 아니라 runtime에서 관찰 |
| 4 | Development history | PR, 이슈, 리뷰, CI 이력 | `gh`, `glab`, 고객 환경의 이슈 트래커 | `gh`만 있음 | 고객 시스템에 따라 선택 |
| 5 | Binary dependency | 소스 없는 사내 framework·library | `javap`, `mvn dependency:sources`, 필요 시 디컴파일러 | `javap`·`mvn` 있음 | |
| 6 | Code semantics | 컴파일러 수준 심볼 정보 | 공식 LSP 플러그인 | 없음 | Serena·CodeGraph는 대형 저장소에서 필요성이 드러날 경우 재검토 |
| 7 | Logs | 로컬 밖 서비스 로그 | `docker logs`, `kubectl logs`, `aws logs` 등 고객 환경의 native CLI | 있음 | |
| 8 | UI | 화면 | Core의 Playwright CLI | 있음 | 현재 구성 유지 |

원문으로 확인하지 않은 것: SQLcl 라이선스 조건, jdtls 오프라인 설치 절차.

### 8.6 여전히 확인되지 않은 것

- 실제 앱에서의 브라우저 확인 (fixture의 FE가 원래 동작하지 않음)
- 결정 항목을 사람이 하나씩 내리는 승인
- 시나리오 A(기능 추가), C(버그 수정)
- 업무급 크기 저장소, 실제 고객 stack
- Bedrock·게이트웨이 경로의 실제 호출, Codex CLI·OpenCode
